# jira-integration Specification

## Purpose

Allow a QA engineer to export a bug report generated by the extension to Jira Cloud as a fully-formed issue, with evidence attached, in one reviewed click — without credentials ever leaving the local browser profile.

## Requirements

### Requirement: Jira connection configuration

The system SHALL let the user configure a Jira Cloud connection consisting of site URL, account email, API token, default project key, and default issue type, stored only in extension local storage.

#### Scenario: Successful connection test
- GIVEN the user has entered site URL, email, and API token in Jira settings
- WHEN the user clicks "Test connection"
- THEN the system calls `GET /rest/api/3/myself` against the configured site
- AND displays the resolved display name and avatar on success
- AND persists the configuration

#### Scenario: Invalid credentials
- GIVEN the user has entered an incorrect API token
- WHEN the user clicks "Test connection"
- THEN the system displays an authentication error with a link to Atlassian's API-token management page
- AND does not persist the configuration as verified

#### Scenario: Host permission granted on demand
- GIVEN the extension does not yet have host permission for the configured Jira site
- WHEN the user saves Jira settings
- THEN the system requests optional host permission for that origin only
- AND aborts setup with an explanatory message if the user declines

### Requirement: Create issue from bug report

The system SHALL provide a "Create Jira issue" action on each generated bug report that opens a pre-filled, editable issue composer, and SHALL only write to Jira after explicit user confirmation.

#### Scenario: Happy path
- GIVEN a Jira connection is configured and verified
- AND a bug report has been generated in the current session
- WHEN the user clicks "Create Jira issue" on the report card
- THEN the composer opens pre-filled with summary, ADF description, labels, priority, project, and issue type
- AND WHEN the user clicks "Create"
- THEN the system creates the issue via `POST /rest/api/3/issue`
- AND displays the new issue key as a link to the issue

#### Scenario: No connection configured
- GIVEN no Jira connection is configured
- WHEN the user clicks "Create Jira issue"
- THEN the system opens Jira settings with a prompt to connect first

#### Scenario: Field validation error from Jira
- GIVEN the target project requires a field the composer did not supply
- WHEN issue creation fails with a 400 field error
- THEN the composer remains open with the user's input intact
- AND the per-field error messages returned by Jira are displayed

### Requirement: Field mapping

The system SHALL map the bug report to Jira fields deterministically: report title → summary (truncated to 255 chars), report body → ADF description, severity → priority (configurable mapping), plus the label `openqa`.

#### Scenario: Description rendering
- GIVEN a bug report containing headings, repro steps, a code block of console errors, and a failed-requests table
- WHEN the composer builds the issue payload
- THEN the description is valid ADF preserving headings, ordered lists, code blocks, and links
- AND any markdown construct without an ADF mapping degrades to plain-text paragraphs rather than being dropped

### Requirement: Evidence attachments

The system SHALL, after issue creation, upload the report's evidence as attachments: screenshots (PNG), the session export (JSON), and the generated Playwright spec (if present), and SHALL report partial failure without failing the whole export.

#### Scenario: Attachment upload
- GIVEN an issue was just created for a report with 2 screenshots and a session export
- WHEN the system uploads attachments via `POST /rest/api/3/issue/{key}/attachments` with `X-Atlassian-Token: no-check`
- THEN all files appear on the issue
- AND the success toast lists the attachment count

#### Scenario: Attachment failure after issue creation
- GIVEN the issue was created but attachment upload fails (e.g. size limit or permission)
- WHEN the failure occurs
- THEN the system still shows the created issue link
- AND shows a warning identifying which attachments failed, with a retry action

### Requirement: Link-back and idempotency

The system SHALL store the created issue key and URL on the bug report and SHALL replace the create action with an "Open <ISSUE-KEY>" link, requiring an explicit "Create another" affordance to duplicate.

#### Scenario: Re-export prevention
- GIVEN a bug report already linked to PROJ-123
- WHEN the user views the report card
- THEN the primary action is "Open PROJ-123" in a new tab
- AND creating a second issue requires the overflow action "Create another issue"

### Requirement: Credential isolation

The system SHALL keep the Jira API token exclusively in extension storage, SHALL send it only to the configured Jira origin, and SHALL NEVER include tokens, Jira payloads, or Jira responses in any LLM prompt or any request to `apps/server`.

#### Scenario: Prompt isolation
- GIVEN a Jira connection is configured
- WHEN any LLM request is constructed
- THEN the serialized prompt contains no Jira configuration values

### Requirement: Error surfaces

The system SHALL translate Jira API failures into actionable messages: 401/403 → re-auth guidance, 404 project → project-key guidance, 429 → retry-after honoured with a single automatic retry, network failure → offline notice with manual retry.

#### Scenario: Rate limited
- GIVEN Jira responds 429 with a Retry-After header
- WHEN the system creates an issue
- THEN it waits the indicated interval and retries once before surfacing an error
